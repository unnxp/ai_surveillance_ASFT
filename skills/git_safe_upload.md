# คู่มือการส่งโค้ดขึ้น Git อย่างปลอดภัยและมีระบบ (Safe Git Upload Playbook)

คู่มือนี้มีวัตถุประสงค์เพื่อนำทางขั้นตอนการผลักโค้ด (Push) ขึ้น GitHub สาธารณะอย่างปลอดภัย ป้องกันรหัสผ่านรั่วไหล และสร้างประวัติการแก้ไขที่มีโครงสร้างตามมาตรฐานสากล

---

## 1. การรักษาความปลอดภัยข้อมูลสำคัญ (Credential Protection)
ห้ามอัปโหลดสตรีม URL หรือรหัสผ่านกล้อง IP ท้องถิ่น ขึ้น Git เด็ดขาด ก่อนกด Stage/Add ให้ปฏิบัติดังนี้:
1. **Masking:** เปลี่ยนลิงก์ที่มีรหัสผ่านจริงในโค้ด (เช่น `rtsp://admin:real_password@real_ip:554`) ไปเป็นตัวแปรจำลองชั่วคราว เช่น `"rtsp://admin:password@192.168.1.100:554/stream1"` ในไฟล์ซอร์สโค้ดทุกจุด
2. **Verification:** รัน `git diff` เพื่อรีวิวความเปลี่ยนแปลงทั้งหมดแบบบรรทัดต่อบรรทัด และค้นหารหัสผ่านจริงว่าไม่มีค้างอยู่
3. **Restore:** หลังรัน Push สำเร็จแล้ว ให้เขียนพาสเวิร์ด/ลิงก์จริงกลับมาทันทีและตรวจสอบ Syntax เพื่อไม่ให้ระบบท้องถิ่นทำงานไม่ได้

---

## 2. การสร้างกิ่งแยกเพื่อตรวจสอบความมั่นใจ (Branching Rule)
* ห้ามผลักโค้ดตรงเข้ากิ่ง `main` หรือ `master` ในเครื่องโดยตรง
* ให้สร้างกิ่งย่อย (Feature branch) สำหรับงานนั้นๆ เสมอ เช่น `feat/risk-assessment-alerts`
* Push กิ่งนั้นขึ้นรีโมต และเมื่อตรวจสอบความถูกต้องจนมั่นใจบน GitHub แล้ว จึงทำการเปิด Pull Request และ Merge เข้าสู่ `main` ภายหลัง

---

## 3. มาตรฐาน Conventional Commits
ทุกๆ Commit ที่สร้างขึ้น จะต้องอยู่ภายใต้รูปแบบมาตรฐานสากลดังนี้:
`<type>[optional scope]: <description>`

### ประเภทของ Commit (Types):
- **`feat`**: พัฒนาฟีเจอร์หรือฟังก์ชันใหม่เข้ามาในระบบ
- **`fix`**: การแก้บั๊กในโค้ดให้ทำงานถูกต้อง
- **`refactor`**: การปรับปรุงสถาปัตยกรรมโค้ดให้อ่านง่าย/เป็นระบบขึ้น โดยไม่ได้เพิ่มฟีเจอร์หรือแก้บั๊ก
- **`docs`**: แก้ไขเฉพาะเอกสารประกอบ หรือคำอธิบาย (Readme, Log, Comments)
- **`style`**: แก้ไขรูปแบบการจัดหน้าโค้ด (Whitespace, Formatting) ที่ไม่มีผลต่อลอจิก
- **`perf`**: การปรับปรุงประสิทธิภาพความเร็วหรือหน่วยความจำในโปรเจกต์
- **`build`**: การแก้ไขพึ่งพิงภายนอก (Dependencies, package.json, requirements) หรือระบบบิลด์
- **`ci`**: การอัปเดตไฟล์คอนฟิกของการตรวจสอบอัตโนมัติ (GitHub Actions, CI)
- **`chore`**: งานจิปาถะอื่นๆ ที่ไม่แตะไฟล์ซอร์สโค้ดหลัก
- **`revert`**: การดึงการแก้ไขเดิมกลับคืน (Rollback/Revert)

### กฎการเปลี่ยนแปลงที่สำคัญ (Breaking Changes):
หากมีการเปลี่ยนโครงสร้างที่ส่งผลกระทบต่อเวอร์ชันก่อนหน้า ให้ใส่สัญลักษณ์ `!` ไว้หลัง Type/Scope เช่น `feat(api)!: change endpoint return format` หรือระบุหมายเหตุ `BREAKING CHANGE:` ไว้ที่ท้ายรายละเอียด Commit

---

## 4. การจัดการ Gitignore
* ตรวจสอบให้แน่ใจว่าไฟล์จำพวก `*.bak`, `data/*` (ข้อมูล Log / ภาพแคปของจริง) และคีย์ความลับไม่โดนดึงเข้าสู่ Git Stage
